# whatsapp-container — handoff

WhatsApp container tooling. The main path is a reusable `wa-agents-service` image that can run multiple independent WhatsApp lines, one container per account.

## Current layout

| Path | Role |
|---|---|
| `setup.sh` | Interactive installer/account manager. Generates `docker-compose.yml`, starts services, and helps pair unpaired accounts. Safe to re-run. |
| `wa-agents-service/` | Combined send/read/incoming service used for both personal and agent WhatsApp lines. |
| `data/<account>/` | New per-account persistent data location generated by `setup.sh`. |
| `.accounts` | Generated account registry: `slug|Label|port`. May not exist until setup migration runs. |
| `.env` | `ADMIN_SECRET`; secret, gitignored. |
## Running services

After `./setup.sh`, containers are named `wa-<slug>` where the slug is the account label lowercased and hyphenated. Each responds on `/api/health` and `/api/status`.

Check what's running:

```bash
docker compose ps
```

## Quick commands

```bash
cd whatsapp-container   # wherever you cloned it

# verify current containers
docker compose ps
curl -s http://127.0.0.1:8792/api/health
curl -s http://127.0.0.1:8793/api/health

# manage accounts / regenerate compose / pair
./setup.sh

# normal lifecycle
docker compose up -d --build
docker compose logs -f
docker compose down
```

If Docker socket access is denied, `setup.sh` now falls back to `sudo docker` when available.

## `wa-agents-service` capabilities

One service instance = one WhatsApp linked-device session with:

- QR pairing and connection status
- admin secret protected settings/token creation
- Bearer-token protected send/read/draft APIs
- outbound send queue with retries
- draft/confirm/cancel safety flow
- read/search endpoints over wacli's local SQLite DB
- incoming polling and SSE updates
- media proxy/decrypt/cache
- browser UI plus `/chat` viewer

See `wa-agents-service/README.md` for the endpoint list.

## Security notes

- WhatsApp Web automation is unofficial. WhatsApp can rate-limit or ban linked numbers. Prefer burner numbers for agent automation.
- Each account/container must have a separate `WACLI_STORE_DIR`. Never share one wacli session directory between running containers.
- Keep the services on LAN/tailnet/reverse-proxy protected surfaces only.
- `.env` and all `data/`/`*/data/` directories contain credentials or message history; do not exfiltrate.

## Current verification gates

These pass from `wa-agents-service/`:

```bash
node --check server.js db.js incoming.js media.js queue.js sync.js wacli-db.js wacli.js public/app.js public/chat.js
```

And from the project root:

```bash
bash -n setup.sh
```
